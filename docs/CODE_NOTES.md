## Quantization

Real-valued dims arrive in `[0, 1]` (or `-1` as a sentinel meaning "no previous transaction"). Both the reference dataset and the per-request query go through the same int16 quantization:

- `[0, 1]` → `[0, 32000]`, half-up rounding via `int16(v*QuantScale + 0.5)`.
- `-1` (sentinel) → `-32000`.

The maximum per-dim squared difference is `32000² ≈ 1e9`. Summed across 14 dims, the squared distance fits comfortably in `int64`, so the inner loop accumulates with no overflow risk.

The intermediate `float64 → float32` conversion in `quantClamp01` is deliberate. The reference dataset's quantization step runs through float32; staying in float64 in the query path produces a 1-unit divergence on values near a quantization boundary. We mirror the float32 step exactly so the same input always quantizes to the same int16.

**The 1 FN we can't eliminate** (entry 5472 in test-data.json) is an inherent cost of int16 quantization: the official labels were generated by **brute-force KNN over float32 vectors**, and the int16 ranking flips one neighbor in the top-5 vs the float ranking. Fixing this would require float32 storage (168 MB — just over our 167 MB cgroup).

## Index — partition + grid (post-revival)

The flat-IVF index from phases 6-8 is gone. The current index has two layers:

### Layer A: 5-bit partition prefilter

The query and every reference vector share a 5-bit key, computed from:

| bit | dim | meaning |
|---|---|---|
| 0 | 9 | `is_online` |
| 1 | 10 | `card_present` |
| 2 | 11 | `unknown_merchant` |
| 3 | 5 (`-32000`?) | sentinel: no last-tx minutes |
| 4 | 6 (`-32000`?) | sentinel: no last-tx km |

`PartitionKey()` returns a `uint8 ∈ [0, 31]`. Vectors with different keys can never be in each other's top-5 (each differing bit contributes ≥1 to squared distance — see lecture 01 §3). So at query time we look only inside the query's own partition.

In practice the dataset uses only 12 of the 32 keys: `(online, card_present)` is never both-true (online implies not-card-present), and the two sentinel bits are always both set or both clear (no last-tx data is all-or-nothing). The other 20 partitions are empty and the search returns 0 immediately for queries that happen to fall there.

### Layer B: percentile-binned grid inside each partition

Inside each non-empty partition, vectors are grouped into a 3D grid with **16 × 8 × 8 = 1024** possible cells (`BinsTotal` in `dataset/dataset.go`). The 3 grid dims are fixed: 0 (`amount`), 12 (`mcc_risk`), 7 (`km_from_home`) — all chosen because none is ever constant in any partition.

Bin boundaries are **percentile-based per partition**: dim 0's 16 bins use the 15 percentile cuts of *that partition's* amount values, not equal-width cuts. This produces approximately balanced cells. Bin assignment is a monotonic scan of bounds (`bin()` in `dataset/grid.go`).

Each non-empty cell stores: a `Start` offset within the partition slab, a `Count`, and `BboxMin`/`BboxMax` ∈ `[Dims]int16` for the axis-aligned bounding box over the cell's vectors. Cells with zero members are omitted entirely — the `Cells []Cell` slice is dense; the 1024-key space exists only conceptually during the build.

Vectors are physically reordered at build time so cells are contiguous within partition, and partitions are contiguous within the file. So `ds.Vectors[(PartitionStarts[p] + cell.Start + i) * Stride + d]` is the d-th dim of the i-th vector of cell `cell` in partition `p` — pure indexing, no indirection.

### Layer C: AABB lower-bound pruning + early-exit kernel (search.FraudCount)

For a query in partition `p` with `g.NumCells` non-empty cells:

1. Compute per-cell **lower-bound distance** `lb(c)`: for each variable dim of the partition, the minimum squared contribution any point inside the cell's bbox can have to the distance. Branches: `q < bboxMin → (q - bboxMin)²`, `q > bboxMax → (q - bboxMax)²`, else 0. Code: `axisLB()`.
2. Sort cell indices by ascending `lb(c)` via insertion sort (in-place, O(n²) but n ≤ 525, ~50 µs worst case).
3. Walk cells in sorted order. For each, if `lb(c) >= topD4`, **break** — no remaining cell can contribute (they're sorted, and topD4 only shrinks). This is the magic line that makes the algorithm sub-1 ms.
4. For surviving cells, run the **early-exit kernel** on each vector: accumulate squared diff dim by dim; if running total `>= topD4`, `continue` to the next vector without computing the remaining dims. Most candidates exit at dim 1-2 once topD4 has converged.
5. Final top-5 maintained as 5 paired `int64`/`uint8` locals (no heap, no slice). The cascading 5-slot insertion is unrolled in `topKInsert()`.

### Why no SIMD

The phase 6 block-major AVX2 kernel (`blockScan8AVX2`) is gone. Early-exit doesn't compose with 8-wide block ops: when most candidates abort at dim 1-2, computing all 16 dims unconditionally for 8 vectors at a time is **slower**, not faster. Variance-ordered scalar early-exit is the right shape for this workload. The kernel is now ~5 lines of obvious Go, BCE-friendly via the `vectors[base:base+Stride:base+Stride]` triple-slice hint.

### Specialized inner loops per partition shape

`FraudCount` branches early on the partition's sentinel state and dispatches one of four specialized scan loops:
- **No sentinels** (11 variable dims: 0-8, 12, 13) — the most common in the dataset
- **Sentinel-5 only** (10 variable dims) — empty in this dataset; carried for correctness
- **Sentinel-6 only** (10 variable dims) — empty in this dataset; carried for correctness
- **Both sentinels** (9 variable dims) — the second most common

Each specialization skips the constant dims entirely, no per-dim mask check at runtime. The variance-ordering of the scan inside each version puts the most discriminating dim first to maximize early-exit hits.

## Custom raw HTTP/1.1 server

We do not use `net/http`. The serving layer is a hand-rolled byte-level HTTP parser:

- `net.Listen("unix", path)` + manual `Accept()` loop, one goroutine per connection.
- Each connection runs `handleRawConn` which loops reading requests on the same socket (HTTP/1.1 keep-alive). HAProxy's `http-reuse always` ensures this amortizes the per-connection setup cost across hundreds of requests.
- `parseRequestLine` extracts only `path` and `Content-Length` (we ignore every other header).
- `RouteRaw` dispatches by exact path match against pre-interned strings.
- Responses are pre-built **full HTTP/1.1 byte arrays** (status line + Content-Type + Content-Length + body) for each of the 6 fraud-count outcomes. `conn.Write(rawhttpResponses[count])` is the entire response code path.

Stdlib `net/http` allocates per request: `http.Request` struct, header map, route parsing. At our target of 1 ms per request, that overhead (~20-50 µs) is meaningful. Custom parsing brings the HTTP layer cost to <1 µs per request.

## Hot-path zero-allocation

The HTTP handler is engineered so a steady-state request allocates nothing on the Go heap:

1. **Body read** — pooled 4 KB `[]byte` slice in `rawReadBufPool`. Bodies are 500–700 bytes; the buffer never grows.
2. **Parse** — `VectorizeFast` writes into a stack-allocated `[dataset.Stride]int16` (`out *[14]int16`). It uses `bytes.Index` (SIMD-accelerated on amd64) to find fixed JSON key sequences, then parses numbers and dates by reading bytes at known offsets. No reflection, no map lookups (`mccRiskTable` is a fixed `[10000]int16`), no `time.Parse`.
3. **Search** — top-K is 5 paired `int64`/`uint8` locals; scratch buffers for cell LBs and sorted indices are stack-allocated `[1024]` arrays inside `FraudCount`. No allocations in the hot path.
4. **Response** — pre-built `rawhttpResponses[0..5]` byte slices.

## Why `GOMAXPROCS(1)`, `GOGC=200`, `GOMEMLIMIT=140MB`

Each API container has a cgroup limit of 0.45 CPU and 167 MB. The Go runtime reads `NumCPU` and sees the host's full CPU count, not the cgroup share — without intervention it spins up 8+ schedulers and oversubscribes. `GOMAXPROCS(1)` aligns the runtime with the actual share.

For memory: the resident dataset (Vectors + Labels + per-partition Grids) is ~95 MB after `LoadIndex`. Default `GOGC=100` doubles the heap before triggering, which would land at ~190 MB — past the 167 MB cgroup, OOM-kill. So:

- `debug.SetGCPercent(200)` — let the heap grow 3× before a GC, since per-request garbage is essentially zero.
- `debug.SetMemoryLimit(140 << 20)` — cap the heap at 140 MB. If anything ever does leak, the GC starts running early instead of letting the OOM killer take over.

## Compose-level tuning

The submission's `docker-compose.yml` has three knobs that matter (see `JOURNEY.md` phase 5):

```yaml
pull_policy: always           # rinha bot must re-pull on every run
ulimits:
  nofile: { soft: 65535, hard: 65535 }
security_opt:
  - seccomp:unconfined
```

`pull_policy: always` was the difference between -2640 (cached broken image) and our first real score. `ulimits` + `seccomp:unconfined` together took us from Err=1 to Err=0 (eliminated the tail-latency HTTP errors under k6 burst load). The seccomp drop matters because the Mac Mini's default seccomp profile filters socket syscalls and adds per-call overhead.

## Dataset distribution — the gotcha

The rinha test infra does **not** mount `references.json.gz` into the container. Submissions are expected to bake it in at build time. Our `deploy/Dockerfile` does this with `COPY references/rinha-official/resources/references.json.gz` and then runs `build-index` to produce `/resources/index.bin` (~87 MB, the persisted partition+grid index). The runtime image only contains `/api` + `/resources/index.bin` — no raw JSON gzip.

Local benches must mirror this: do **not** mount `/resources` as a volume override (that would hide the in-image copy and pass on Rosetta while the rinha env fails). The local override only bumps HAProxy memory (Rosetta JIT overhead).

## Build-time vs runtime layout

The index pipeline has two halves:

**Build-time (`cmd/build-index/main.go`)** — runs inside the Docker builder stage, no cgroup:
1. `LoadFromGzipJSON` decompresses + parses references.json.gz, producing `ds.Vectors` (flat int16, stride 14) + `ds.Labels` (flat uint8) in source order.
2. `BuildGrid` runs two in-place permutations: first by partition key (5-bit prefilter), then within each partition by 10-bit cell key. Both use the standard swap-permute routine (`swapPermuteRows`) — O(N) total swaps with one Stride-sized scratch row.
3. `SaveIndex` writes header + vectors + labels + per-partition grid records to `/resources/index.bin` (~87 MB).

Total build time: ~4 s for the gzip load + ~1 s for the grid build + 20 ms write = ~5 s total. Was ~25 s in the IVF era.

**Runtime (`cmd/api/main.go`)** — runs inside the 167 MB cgroup:
1. `LoadIndex` reads `/resources/index.bin` directly into `ds.Vectors`, `ds.Labels`, `ds.PartitionStarts/Counts`, `ds.Grids`. No partition build, no cell sort, no bbox compute — milliseconds of work.
2. Start the raw HTTP server, mark `/ready` healthy. Set `GOGC=200`, `GOMEMLIMIT=140 MB`, run one `runtime.GC()` to consolidate the heap.

This separation is what makes our startup pass the rinha bot's health-check timeout: an in-process grid build over 3M vectors takes ~5 s — well under the bot's grace window, but still better to pre-bake.
