# Code Notes

Design and implementation context for the Go submission. Source files are kept comment-light on purpose; everything that would otherwise have lived in a paragraph-long docstring is here.

For the trajectory of how we arrived at this design (and the architectures we tried and abandoned), see `docs/JOURNEY.md`. For the higher-level problem statement and algorithm walkthroughs, see `docs/lectures/`.

## Quantization

Real-valued dims arrive in `[0, 1]` (or `-1` as a sentinel meaning "no previous transaction"). Both the reference dataset and the per-request query go through the same int16 quantization:

- `[0, 1]` → `[0, 32000]`, half-up rounding via `int16(v*QuantScale + 0.5)`.
- `-1` (sentinel) → `-32000`.

The maximum per-dim squared difference is `32000² ≈ 1e9`. Summed across 14 dims, the squared distance fits comfortably in `int64`, so the inner loop accumulates with no overflow risk.

The intermediate `float64 → float32` conversion in `quantClamp01` is deliberate. The reference dataset's quantization step runs through float32; staying in float64 in the query path produces a 1-unit divergence on values near a quantization boundary. We mirror the float32 step exactly so the same input always quantizes to the same int16.

**The 1 FN we can't eliminate** (entry 5472 in test-data.json) is an inherent cost of int16 quantization: the official labels were generated by **brute-force KNN over float32 vectors**, and the int16 ranking flips one neighbor in the top-5 vs the float ranking. Fixing this would require float32 storage (168 MB — just over our 167 MB cgroup).

## IVF index — flat K=8192 with balanced KD-split

We **do not** use Lloyd k-means. Instead, the dataset is partitioned via a recursive median-split on the max-variance dimension. Pseudocode:

```
balancedSplit(ids, start, end, clusterBase, clusterCount):
    if clusterCount == 1:
        clusters[clusterBase] = ids[start:end]
        return
    dim := arg-max-d Var(ids[start:end] on dim d)
    sort ids[start:end] by vectors[id][dim]
    mid := (start + end) / 2
    half := clusterCount / 2
    balancedSplit(ids, start, mid, clusterBase, half)
    balancedSplit(ids, mid, end, clusterBase+half, half)
```

Properties:
- **Exactly balanced cluster sizes** (±1 vector each). With K=8192 over 3M vectors, every cluster holds 366 ± 1 vectors.
- Build time is O(N log K · D) ≈ `3M × 13 × 14` ≈ 550M ops — completes in seconds, not minutes.
- The discrete dims (`is_online`, `card_present`, `unknown_merchant`, sentinel bits) get split early since they're high-variance — so each leaf cluster has homogeneous values on those bits.

**Why we abandoned k-means.** Lloyd k-means on this data produces unbalanced clusters (some 1500+, some <100) AND meaningless centroids on the binary dims (centroids end up at intermediate values like 16000 for a binary 0/32000 dim). The `nprobe` heuristic then misses neighbors that sit in adjacent small clusters. Balanced split sidesteps both problems.

## Search — fast probe + ambiguity expansion

At query time:
1. Compute **centroid distances** to all 8192 clusters using the batched 8-wide SIMD kernel (`blockScan8AVX2` over centroid blocks). Centroids are stored in dim-major block-major layout so the kernel runs at maximum throughput.
2. Pick the **top `IVFNProbe = 32`** clusters by centroid distance ascending.
3. Scan those 32 clusters' vectors via the same `blockScan8AVX2` kernel. Track the top-5 nearest with their labels.
4. **If `fraud_count ∈ {2, 3, 4}`** (borderline — within 1 of the deny/approve threshold), expand probes to `IVFAmbiguousNProbe = 128` and re-scan. The top-5 carries over and the additional clusters either tighten the bound or get skipped via `dist >= d4` continue.
5. Tally fraud labels in the final top-5.

**Trade-off.** The fast path scans 32 × 366 ≈ 11,700 vectors per query at ~5 ns SIMD per vector ≈ 60 µs CPU. The ambiguity path scans 4× more (~47k vectors) but only ~10-20% of queries trigger it. Average CPU per query stays under 150 µs.

**Accuracy.** Verified against brute-force on all 54,100 test entries: 12 mismatches that cross the approve/deny threshold (FP=4, FN=8), out of 24,058 frauds + 30,042 legit. Compare to the old partitioned IVF (FP=0, FN=1) — flat is approximate but the per-query CPU drop more than compensates in the final score.

## Block-major SIMD kernel

Each cluster's vectors are stored in **dim-major 8-wide blocks**:

```
Block layout (256 bytes per block, 8 vectors per block):
   [dim 0, vec 0..7]   ← 16 bytes
   [dim 1, vec 0..7]
   ...
   [dim 15, vec 0..7]
```

The AVX2 kernel `blockScan8AVX2` (in `internal/search/blockdist_amd64.s`) processes one block per call, producing 8 squared distances in parallel:

```
For each dim d ∈ 0..15:
    VPBROADCASTW [query + d*2], X2    // 8 copies of query[d]
    VMOVDQU      [block + d*16], X3   // 8 ref values for dim d
    VPSUBW       X2, X3, X3           // 8 int16 diffs
    VPMOVSXWD    X3, Y3               // sign-extend to int32
    VPMULLD      Y3, Y3, Y3           // diff² as int32
    Sign-extend each half to int64 and accumulate into Y0, Y1
```

After 16 dims, Y0 (low 4 vectors) + Y1 (high 4 vectors) hold the 8 squared distances. Memory write to `out[8]int64`.

The same kernel is used for both centroid distance and per-vector cluster scan, so the centroid block layout matches the cluster block layout exactly.

**Why int16 + int64 accumulation, not float32 + FMA.** Float32 with VFMADD231PS is a hair faster per op, but the memory footprint doubles (168 MB > our 167 MB cgroup). We accepted the 1 quantization FN to stay inside the memory budget.

## Custom raw HTTP/1.1 server

We do not use `net/http`. The serving layer is a hand-rolled byte-level HTTP parser:

- `net.Listen("unix", path)` + manual `Accept()` loop, one goroutine per connection.
- Each connection runs `handleRawConn` which loops reading requests on the same socket (HTTP/1.1 keep-alive). HAProxy's `http-reuse always` ensures this amortizes the per-connection setup cost across hundreds of requests.
- `parseRequestLine` extracts only `path` and `Content-Length` (we ignore every other header).
- `RouteRaw` dispatches by exact path match against pre-interned strings.
- Responses are pre-built **full HTTP/1.1 byte arrays** (status line + Content-Type + Content-Length + body) for each of the 6 fraud-count outcomes. `conn.Write(rawhttpResponses[count])` is the entire response code path.

Stdlib `net/http` allocates per request: `http.Request` struct, header map, route parsing. At our target of 1 ms per request, that overhead (~20-50 µs) is meaningful. Custom parsing brings the HTTP layer cost to <1 µs per request.

## Hot-path zero-allocation

The HTTP handler is engineered so a steady-state request allocates nothing on the Go heap:

1. **Body read** — pooled 2 KB `[]byte` slice in `rawReadBufPool`. Bodies are 500–700 bytes; the buffer never grows.
2. **Parse** — `VectorizeFast` writes into a stack-allocated `[dataset.Stride]int16` (`out *[16]int16`). It uses `bytes.Index` (SIMD-accelerated on amd64) to find fixed JSON key sequences, then parses numbers and dates by reading bytes at known offsets. No reflection, no map lookups (`mccRiskTable` is a fixed `[10000]int16`), no `time.Parse`.
3. **Search** — `topK` is a value type with 5 distance/label slots; lives on the stack. Centroid distances and cluster scratch are stack-allocated.
4. **Response** — pre-built `rawhttpResponses[0..5]` byte slices.

Per-request micro-bench on Apple M4 Pro: **429 ns/op for parsing, 0 allocs**.

## Why `GOMAXPROCS(1)`, `GOGC=200`, `GOMEMLIMIT=140MB`

Each API container has a cgroup limit of 0.45 CPU and 167 MB. The Go runtime reads `NumCPU` and sees the host's full CPU count, not the cgroup share — without intervention it spins up 8+ schedulers and oversubscribes. `GOMAXPROCS(1)` aligns the runtime with the actual share.

For memory: the resident dataset (Blocks + BlockLabels + CentroidBlocks + IVF metadata) is ~100 MB after `LoadIndex`. Default `GOGC=100` doubles the heap before triggering, which would land at ~200 MB — past the 167 MB cgroup, OOM-kill. So:

- `debug.SetGCPercent(200)` — let the heap grow 3× before a GC, since per-request garbage is essentially zero.
- `debug.SetMemoryLimit(140 << 20)` — cap the heap at 140 MB. If anything ever does leak, the GC starts running early instead of letting the OOM killer take over.

## Compose-level tuning

The submission's `docker-compose.yml` has three knobs that matter:

```yaml
pull_policy: always           # rinha bot must re-pull on every run
ulimits:
  nofile: { soft: 65535, hard: 65535 }
security_opt:
  - seccomp:unconfined
```

`pull_policy: always` was the difference between -2640 (cached broken image) and our first real score. `ulimits` + `seccomp:unconfined` together took us from Err=1 to Err=0 (eliminated the tail-latency HTTP errors under k6 burst load). The seccomp drop matters because the Mac Mini's default seccomp profile filters socket syscalls and adds per-call overhead.

## Dataset distribution — the gotcha

The rinha test infra does **not** mount `references.json.gz` into the container. Submissions are expected to bake it in at build time. Our `deploy/Dockerfile` does this with `COPY references/rinha-official/resources/references.json.gz` and then runs `build-index` to produce `/resources/index.bin` (~140 MB, the persisted IVF). The runtime image only contains `/api` + `/resources/index.bin` — no raw JSON gzip.

Local benches must mirror this: do **not** mount `/resources` as a volume override (that would hide the in-image copy and pass on Rosetta while the rinha env fails). The local override only bumps HAProxy memory (Rosetta JIT overhead).

## Build-time vs runtime layout

The index pipeline has two halves:

**Build-time (`cmd/build-index/main.go`)** — runs inside the Docker builder stage, no cgroup:
1. `LoadFromGzipJSON` decompresses + parses references.json.gz, producing `ds.Vectors` (flat int16) + `ds.Labels` (flat uint8).
2. `BuildIVF` runs `balancedSplit` (above), computes per-cluster centroids and bboxes, then **transposes `ds.Vectors` to `ds.Blocks`** in dim-major 8-wide layout. Labels are remapped to `ds.BlockLabels` in the same block order.
3. `SaveIndex` writes Blocks + BlockLabels + Centroids (block-major) + per-cluster metadata to `/resources/index.bin`.

**Runtime (`cmd/api/main.go`)** — runs inside the 167 MB cgroup:
1. `LoadIndex` reads `/resources/index.bin` directly into `ds.Blocks`, `ds.BlockLabels`, `ds.IVF.CentroidBlocks`, `ds.IVF.Clusters`. No k-means, no transpose — milliseconds of work.
2. `ds.Vectors` and `ds.Labels` are never populated at runtime (they exist only for build-time and tests).

This separation is what makes our startup pass the rinha bot's health-check timeout: an in-process k-means build over 3M vectors takes 30+ seconds, which the bot does not tolerate.
